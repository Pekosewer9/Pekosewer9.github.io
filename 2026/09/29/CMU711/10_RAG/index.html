10.Retrieval and RAG

|Post Views:

Limitation of LMS: Hallucinations(幻觉)

  • 论文引用的title，人名，等信息是错的

问题：模型不可能记住所有的预训练数据中的信息
而且新的信息没有在预训练练集里面

Retrieval-Augmented LMs(RAG)

Datastore/ Retriever / LM

我们用query来查询数据库中的信息， 选出top-k， 我们用这些数据增强我们的LM模型

  1. Sources of data
  2. how to retriever : architecture, train, evaluation
  3. LM:Architectures, Training Inference

Source of data

  1. Scaling up Datastore
    用B-Tree索引一个包含所有预训练数据的数据库(1.4trillion tokens)
    但是这样会需要很大的内存和效率

  2. Processing Documents

  3. 我们把像HTML的这种数据转化成pure text

  4. 我们把它们chunking成更小的单元， 我们通常用split by paragraph 或者 每200个token之类的， 再进行remove

  5. filtering:把不符合要求的去掉

Retriever

  • types of Retrievers
  1. Sparse retrievers : embedding是关于术语的频率
  2. Dense retrievers(more effective) : 训练LM去生成embedding
  3. Rerankers(性能更好) : scores based on jointly encoded query and doc
  • sparse Retrievers : 用one-hot Vector(只有1和0)， count vector(加上计数)

*用weighted_term vectors

  • 文档d中这个词t的频率 * 词语t在整个文档中提供的信息量（总文档数 / 包含这个词语t的文档总数）, 包含这个词文档总数越少， 我们认为这个词在区分文档和其他文档不同这一方面越重要

  • 我们把每一个这个TF-IDF分数编入weighted-term vectors

  • 之后我们用query 和 di 去计算cosine similarity
    注意：我们这里query文档的向量仍然是基于TF-IDF，但是IDF(t) 仍然是基于整个文档集合(corpus)

  • Dense retrievers

  • 我们用 Encoder model生成Query和d的向量， 再计算相似度

  • 我们可以用Bert的Only_Encoder编码的CLS的输出向量

  • 但是现在的LM 很多都是 only-decoder(每一个字符生成的output vector之和前面的注意力有关， 所以可以用mean/pooling的输出向量)

Training Dense Retrievers

  • 我们用对比学习
  • 我们每次用一个query, 一个正样本和n个负样本训练，最小化L

我们需要一个很快的nearest neighbor search(因为文档chunk量会很大)

  1. 数据量小 -> 精确search
  2. 数据量大 -> approximate search
  3. 减少index_size -> quantization

reranking with cross encoders
在上面的阶段, 我们用Bi-Encoder（独立Encoder）（cheaper encoder）快速从海量文档中召回Top-K个候选文档 k =100/500
在reranking过程中， 我们Query和每一个top-K的文档可以进行full-self-attetion,可以互相计算cross_entropy, 然后经过classifier输出一个相关性得分

Evaluation Metrics:

可以关注到底有没有关联， 和分数的排名是不是和实际情况相干
benchmark: MTEB
BEIR RESULTs

  • Dense retrievers 会在OOD上表现不佳

How to Use Retrieval

  1. input augmentation: 我们把检索来的信息加入prompt的输入里面
  2. intermediate Fusion: 提取检索来的信息在hidden_state和原来的模型输出的信息融合
  3. output interpolation

input augmentation: 容易集成，表现较好
[RAG Lewis at al. 2020]

training input RAG

End to end Training for RAG:

  • 我们像原来一样训练， 但是我们把Retriever score和 Gneratore score 一起计算， 同时反向传播可以传播到query encoder和 retriever里面

因为文档向量是在向量数据库里的， 不会随着反向传播而更新，所以我们需要对文档和查询的结果进行重新更新， 之后还要计算和排序

异步/间隔更新（Periodic Update）：模型训练 $N$ 个 Batch（例如每 1000 步）才在后台统一刷新一次全量 Chunk 向量和向量库索引。
局部/In-Batch 实时更新（In-Batch / Top-K Update）：训练时只对当前 Batch 内用到的候选 Chunk（比如召回的前 50 个 Chunk）在显存里实时重新算向量和相似度，其他未用到的远端 Chunk 暂时保持不动，以此平衡计算开销与训练准确性。

很多人不进行RAG训练， 直接丢给现成的大模型

IN-context RAG

在长尾问题(比较少人问的问题)上， GPT3 + Retrieval 表现得更好
但是在popular问题上， GPT3 + REtrieval 反而不如GPT3

容易be disled by the unhelpful information

Self-RAG:Adaptive Retrieval(只有在需要的时候RAG)

  • 我们要先训练language model 是否要 retrieval

  • 我们还要训练LM 这些文件是否是relevant的， 如果relevant才输入文本

tool-augmented LMs

  • 除了retrieval,模型还可以选择不同的工具去调用
  • 长距离的single generation可能有不同的答案， 不能单纯用词元预测

我们用logical units verification来对中间生成步骤进行打分和约束
我们用一组评估标准的{True,False}来判断

but, input augmentation has many limitation’

  1. 文档很多
  2. model 不一定会被这些输入的文档约束

intermediate fusion -> 吧、改变原来的transformer机构

google 的 RETRO:

在Attention和FFW层中间加一个CCA层， 加入Encoded neighbors的信息

output interpolation(直接作用于输出token的概率分布)

KNN-LM：
对两个进行概率分布加权求和

将预训练 LM（Decoder-only）在预测每一个 Token 时生成的隐藏状态（Hidden State）作为 Key，将真实的下一个 Token 作为 Value，存在一个巨型向量库中。推理时，通过 $k$NN 检索最相似的上下文，并将检索到的 Token 概率与原语言模型的 Softmax 概率进行线性插值（Interpolation）。

将λ设的很大， 能有效解决OOD问题

Q:RAG vs Fine_tuning

  • 有足够高质量的训练对的话微调会很好

RAG vs search_API

  • search_engine changes everyday
