Evaluate our model

  • validation loss 不一定和 solve rate 相关
  1. 伪过拟合（Grokking / Task Alignment）
    在针对特定领域（如 AlphaCode 的竞赛编程）进行微调时：

通用语言能力的 Loss 在上升： 模型在微调过程中逐渐“遗忘”了通用预训练数据中的自然语言语法和多样表达（导致通用 validation loss 上升）。

特定任务能力的 Solve Rate 在上升： 模型将参数权重高度集中到了特定任务（如解题、生成约束代码）的模式匹配上。

  1. 概率校准退化（Overconfidence / Miscalibration）与过拟合
    当
    对大模型进行长时间微调（Finetuning）时：

模型对预测过于自信，极度压低了某些不常见词的概率。如果模型在一个不影响最终正确性的非关键 Token（比如代码中的变量名或标点）上预测失误，交叉熵损失就会受到极大惩罚（Log-loss 呈对数级激增），导致 Validation Loss 上升。

但这种概率校准的失效，并没有改变模型选择最关键推理步骤/正确词汇的相对排序（Argmax）。模型的决策边界仍然有效，甚至在关键逻辑

Loss只是测量模型是否符合data distribution; 但是它不直接测量how well a model perform task

Task metrics and downstream evaluation

benchmark consist of

  • A dataset D(sometimes only inputs x)
  • A task metric m(m(y,y_))

Create a benchmark

Example: MMLU

  1. 好验证， 出结果快
  2. 无法考验模型文本输出能力

Example: HumanEval

pass@K: 尝试k times 去看是否有一次通过了全部测试点

Example: GSM8K

我们会生成CoT, 但是最后检查的Metric还是最后的答案
-> 但是我们无法保证这里的CoT是正确的
-> 考虑到生成数据的effeciency

Good Benchmarks:

  1. Breadth and diversity
  2. depth and difficulty to distinguish the good and bad models
  3. utility
  4. robustness(相同问题或者相似问题不同情况下问都输出争取额答案)
  • ICL:模型会在benchmark的反馈中in context learning, 改变下一次的策略

Data contamination: 数据被泄露或者有类似的数据被进入模型的训练数据集

  • 用recent problems防止数据污染

我们怎么评估长文本的输出？

Example: what are some business etiqutte norms when doing business in Japan

  1. (传统方法) word overlap
    根据参考答案的字计算准确率和召回率
    cons : 没有语义相似性， 也不好获取reference
  2. use LLM as a judge
    直接将两个答案输入LLM, 再输入合适的Prompt, 让它output 一些 scores
    LLM-as-a-Judge 的偏见（Bias）： 判定模型倾向于偏爱长文（Verbosity Bias）、位置偏好（Position Bias）以及自我偏好（Self-Enhancement Bias）。
  3. checklist-based evaluation
    给出一个条款清单， 让LLM judge去检查这些criterion被满足了吗（1/0）
    尤其在评测agent/ code能力中很有用
  4. use humans
    ask human vote which response is better
